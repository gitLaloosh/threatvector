Intel sound: a refused file's warning goes at the slot's next press

Page 2026-11-11 · v2026.11.11.1

Why

  • Build queue 033, Project doc roadmap/intel-sound-warning-plan.md. A user's report, passed on by the owner: "The warning for a sound file thats too large persists after swapping back to a built in one."
  • Cause: a refused file (over 1 MB, INTEL-09; not sound, INTEL-10) leaves the slot an entry with only the warning, and choosing a built-in cleared the entry only when it held a file. After a refusal the list still shows the slot's sound, so choosing that same sound again fires no change at all.
  • Decided at the build review (the owner's A): pressing the slot's list, or opening it from the keys, also clears the warning, so choosing the same sound again works; the focus alone doesn't (the page puts the focus back on the list after a refusal, which would hide the warning before it's read).

What changed

  • Choosing a built-in clears the slot's warning as well as any file.
  • The slot's list pressed (pointer) or used from the keys (any key but Tab, Shift, Ctrl, Alt, Meta, Escape, Caps Lock), "Your own file…" and ▶ Test clear that slot's old warning (itSndMsgDrop). A new refusal shows it again.
  • The line is taken off the page as it is, never by redrawing the card: a redraw on the list's press would replace the list under the pointer, and the file picker's input lives in the card. The card's last build is forgotten (it.lastHtml = null) so the same warning again is drawn.
  • Nothing else: the limits, the texts INTEL-09/10, storage (no stored data changed; the warning lives in memory only), volume, Test, notifications.

Checks

  • alert_sound_check.py, warn_cases: a different built-in (INTEL-09 and INTEL-10); the list pressed and opened from the keys (the same list element after the press, still gone after a redraw); Tab and the page's own focus keep it; the same refusal right after a drop is shown; ▶ Test (the focus stays on it); "Your own file…" then cancel (the same file input) and a pick after it; a kept file plus a refused second file; 390 px, the box's height back after.
  • Six mutants each fail those cases: the old handler (the bug), a press redrawing the card, the last build not forgotten, the focus clearing it, ▶ Test not clearing it, Tab clearing it.

Lesson for future models

LESSON #152: a press can't redraw the view that holds the control pressed (a list must still open, a file picker's input must survive). Change that part in place, and make the view forget its last build, or the next identical state is skipped by the compare.
