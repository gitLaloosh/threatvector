Log in with EVE (SSO Phase 1: who you are, nothing else)

Page 2026-11-08 · v2026.11.08.1

Why

  • Build queue 024, Project doc roadmap/sso-phase1-plan.md (parent plan roadmap/eve-sso-plan.md, Phase 1); the clickable prototype from the Project's roadmap/sso-login-mockup/, set to the owner's choices: CCP's black button, above the typed name, Log out clears the pilot, the login per tab, no permissions.
  • The owner, on keeping the login optional: "the UI implementation needs to be pretty straight forward if it's going to work."
  • Phase 0 (build queue 023, v2026.11.07.3) put in the page's security policy, the escaping lint and the request-gate rule this builds on.

What changed

  • The profile's Pilot section: CCP's "Log in with EVE Online" image (black, large, 270 × 45, unaltered: DLA 7.2) in a button, one line "Only says who you are, for this tab" with an info panel ("How logging in with EVE works", the plan's four paragraphs), "or type it", then the typed field as before. Logged in, the field becomes the name, an "EVE login" tag and Log out; "Logged in for this tab" under the corporation line. The disabled "Log in with EVE (later)" button is gone.
  • How it works: CCP's PKCE recipe for a page without a server. The press makes a verifier, its S256 challenge and a state, keeps them in this tab's sessionStorage, and goes to CCP's authorize address (read from CCP's metadata) with the origin's Client ID and no scope. Coming back, the code and state are taken out of the address at the very top of the script (SSO_RET), before the page asks anything of anyone; the state is checked (this tab's, under 10 minutes old, used once); the code is exchanged; the access token is checked with WebCrypto against CCP's keys (the key its kid names, RS256 with the RSA key or ES256 with the P-256 key only; issuer, audience with the Client ID and "EVE Online", expiry, CHARACTER:EVE:<id>); the pilot is set by its ID (sideSetPilotId, the same affiliation code as typing it).
  • Tokens: the access token stays in memory and goes nowhere in this phase. The refresh token and the character's ID and name are in sessionStorage, so a reload keeps the login (nothing is fetched) and a new tab asks again. Log out revokes the refresh token at CCP, clears the keys and the pilot, and links EVE's page of authorized apps (through the page's "Open EVE's community site?" question). CCP has no logout page for apps, so the player stays signed in on EVE's own site (the next login is usually one click, as the info panel says); nothing on the page promises more. Another tab changing the pilot logs this tab out, with one line saying so
  • CCP's image is left as CCP made it (CCP: "please use one of the following images for the button"): hover draws an outline on the button around it and focus the page's cyan ring; no filter, opacity or resize on the image.
  • The Client ID comes from the page's address: threatvector.space uses the production app, http://localhost:8000 the dev app; anywhere else (a saved copy) the button is disabled with the title "EVE login works only on threatvector.space".
  • Errors SSO-01 (cancelled), SSO-02 (not this tab's, too old or used), SSO-03 (CCP's login unreachable or answering oddly: only JSON is read, an HTML error page is its status number), SSO-04 (the token didn't check out), SSO-05 (the code expired). Each says to press the button again; none changes what's saved.
  • Kept in the browser: new sessionStorage keys tvSsoPending, tvSsoWho, tvSsoRefresh (this tab only). Nothing new in localStorage. An older page ignores the new keys; a newer page reads everything the older one wrote.
  • Differences from the plan: the plan gave the token's sub as EVE:CHARACTER:<digits>; CCP's tokens carry CHARACTER:EVE:<digits> (CCP's page on validating the token), and the page checks CCP's form. The authorized-apps address is the research session's candidate (community.eveonline.com/support/third-party-applications, from a 2022 wiki), kept in SSO_APPS_PAGE and confirmed in the owner's hand test. The line under the button is "Only says who you are, for this tab": the plan's wording ran over the 40-character limit for such lines. The info panel's key is side#sso (a variant of the Standings card, as the subtext rule asks).

Checks

  • New sso_check.py, never a live login: the page served at both apps' addresses by routes, a stand-in for CCP's login with keys made for each run and tokens signed in the test, a revoke that records what it got. It checks the logged-out layout, the press (every parameter, no scope, the challenge from the verifier, the production ID on threatvector.space), the return (the address cleaned before any request, the token request, the logged-in row, the tokens' storage), reload, a new tab, another tab clearing the pilot, Log out, every refusal (19 kinds, each its code and nothing saved changed), a saved copy, and 1440 and 390 px.
  • check_request_gates.py: ssoFetch is the one fetch() to CCP's login (its host only, before the fetch; no cookies), called only from SSO_SITES; the host is written once. csp_check.py: the button's image and a request to CCP's login under the policy. check_pii: the button image reviewed and listed.
  • Mutants: MUTANTS_LINE
  • CHECKS_LINE
  • Page size: SIZE_LINE

Lesson for future models

  • LESSON #147: a format a plan writes down is a claim, not a source. The plan's sub form was the wrong way round; a stand-in built from the plan would have agreed with the code, and every real login would have failed. Check each exactly-matched field against the provider's own page before it becomes code, and say in the pull request where the plan was wrong.
