The patch-day report and text ids

Tools 2026-11-11 · page unchanged (after v2026.11.11.1) · build queue 034

Why

  • The "Jump table" workflow's game-data job failed on CCP's build 3682781 (two scheduled runs in a row): ValueError: invalid literal for int() in chain() of tools/sde_change_report.py, on a UUID.
  • That build's changes file has tables whose ids are text (UUIDs): characterTitles, militaryCampaigns, militaryCampaignObjectives (CCP's changes/3682781.jsonl, checked 2026-11-11). chain() turned every table's ids into numbers, though the report reads five.
  • So the report that lists what EVE's update changed, the starting list for the pyfa update, wasn't being made.

What changed (tools only)

  • chain() reads only the tables the report uses (USED: types, typeDogma, groups, dogmaEffects, dogmaAttributes), skipping the rest before any conversion; main() uses the same constant.
  • An id in those five that isn't a whole number is skipped and said: a warning in the job's log and a bold line at the top of the report (so in the pull request text too), naming the table, the count and up to 3 examples (the owner: "Log and report").
  • The check (check_sde_change_report.py case 8): a stand-in changes file with two UUID tables and an id in types that isn't a number. Same list as without them, the warning in the log, the report and the pull request text, no unused table named. Two mutants (int() on every table as before; int() on every id of the five) fail it.
  • In the fast lints now (the owner: "yes"): it takes about 2 seconds and needs no network; before, it ran only in pyfa_update_check.py's chain.
  • Looked at, unchanged: tools/jump_table_update.py reads three map tables from CCP's zip (stargates, solar systems, regions; number ids) and never reads the changes files; its job passed on both failed runs. tools/gen_intel_tables.py reads pyfa's and the client's files, not CCP's changes files.
  • .github/workflows/ unchanged; nothing kept in browsers changes.

Not in this delivery

  • The pyfa update for the expansion (pyfa v2.70.0): its own item, starting from the report this makes.
  • No run against CCP's live data from the build session (no route to CCP's site from it): the owner's run of the workflow after the merge is the live test. The report then covers the newest build at or before the verified one (3624425) up to 3682781, so the list replaces the page's current one (made for 3670638).

Lesson for future models

LESSON #153: read only the parts of an outside file you use, and expect any part to change form. A table the report never needed stopped it; in the parts you do read, skip a value in an unexpected form and say so where the owner looks, and test with a stand-in file that has a part in another form.
