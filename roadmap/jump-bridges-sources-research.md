# Research: where other EVE tools get alliance jump bridge lists (2026-11-12)

Research session, for build queue 041 (`claude/roadmap/jump-bridges-plan.md`). Asked by the owner: [stated] "find out how other eve tools get their jump bridge data for alliances", then "include rift", then "yes" to folding the result into 041's plan and saving it here; then "yes" to reading CCP's ESI spec in his built-in browser; then "can we test it?" (the search).

## Summary
ESI has no route that lists an alliance's Ansiblex bridges, so every tool works around it in one of three ways: a pasted list (most tools), a character's structure-name search, or a director reading the corporation's structures. A pasted list is what 041 already plans; the result for the plan is to read the formats those tools use (below). RIFT, a large and widely used tool, most likely uses the structure-name search (see its row). CCP's current ESI spec (read 2026-11-12) confirms that no structure route a line member can use lists bridges; the search + structure lookup is the only login route. **But CCP has said, in its own developer blog (2018-06-19), that using the search endpoints as a discovery mechanism is abuse of the API, met with bans (next section).**

## CCP's rule on search for discovery
- CCP's developer blog "The ESI API is a shared resource, do not abuse it" (Team Tech Co, 2018-06-19): "From this point forwards, using the search endpoints as a discovery mechanism will be considered abuse of the API", met with bans, after a one-week grace period "for people to turn off their scrapers". It doesn't mention structures. (source: https://developers.eveonline.com/blog/article/the-esi-api-is-a-shared-resource-do-not-abuse-it, CCP's developer blog, checked 2026-11-12)
- esi-issues #616 (a users' request for a route listing structures a character can access, open, no CCP reply) quotes that post as the reason authenticated /search may no longer be used to find structures. (source: https://github.com/esi/esi-issues/issues/616, CCP's ESI issue tracker, checked 2026-11-12)
- Reading: searching " » " to find structure ids you don't already know is "the search endpoints as a discovery mechanism", whether done once by hand or by a tool for each user. Whether CCP enforces it against a user-started, one-search-per-login use (RIFT appears to do this) is UNVERIFIED: only CCP can say; the risk falls on the app (its client ID) and every user of it. The blog's tone ("scrapers") is about bulk scraping, but its wording isn't limited to that.

## No ESI route
- The request for a jump bridge route has been open on CCP's ESI issue tracker since 2018; no CCP reply, not closed. Users there suggest reading the corporation's structures and parsing names; one (a community member, not CCP) says scraping the search endpoint for discovery isn't allowed (now backed by CCP's blog above). (source: https://github.com/esi/esi-issues/issues/1084, CCP's ESI issue tracker, checked 2026-11-12)
- Eveeye's docs: "no api available to add jump bridges to the maps". (source: https://eveeye.readthedocs.io/en/latest/sharing/jumpbridges/, the tool's own docs, checked 2026-11-12)
- CCP's Equinox ESI post (2026-05-19) adds sovereignty hub, skyhook, mercenary den, access list and sovereignty system routes; it names no scopes and says nothing about Ansiblex bridges. (source: https://developers.eveonline.com/blog/equinox-on-esi-structures-sovereignty-and-access-lists, CCP's developer blog, checked 2026-11-12)

## CCP's ESI spec (read 2026-11-12 in the owner's built-in browser)
Source: https://esi.evetech.net/meta/openapi.json (CCP's ESI OpenAPI spec; the default answer is compatibility date 2020-01-01, 182 routes; with `?compatibility_date=2026-11-12` it answers version 2026-08-18, 218 routes), checked 2026-11-12. Every route whose path has "structure" or whose scopes are structure scopes:
| Route | Scope | What it is |
|---|---|---|
| GET /characters/{character_id}/search | esi-search.search_structures.v1 | "Search on a string": `categories` (required, includes `structure`), `search` (required, minLength 3), `strict` (default false); the answer's `structure` field is a list of int64 ids, nothing else |
| GET /universe/structures/{structure_id} | esi-universe.read_structures.v1 | "Returns information on requested structure if you are on the ACL. Otherwise, returns \"Forbidden\""; fields name, owner_id, position, solar_system_id, type_id (required: name, solar_system_id, owner_id) |
| GET /universe/structures | none | "List all public structures" (ids; a structure with any ACL restriction isn't in it) |
| GET /corporations/{corporation_id}/structures | esi-corporations.read_structures.v1 | the corporation's own structures (a Director, per CCP's ESI docs) |
| GET /characters/{character_id}/structures/mercenary-dens (+ /{id}) | esi-structures.read_character.v1 | Mercenary Dens: the ONLY routes this scope opens |
| GET /corporations/{corporation_id}/structures/skyhooks (+ /{id}) and /sovereignty-hubs (+ /{id}) | esi-structures.read_corporation.v1 | Skyhooks and Sovereignty Hubs: the ONLY routes this scope opens |
| GET /markets/structures/{structure_id} | esi-markets.structure_markets.v1 | orders in a structure (not relevant) |

So: the two esi-structures scopes have nothing to do with jump bridges (RIFT likely asks for them for its sovereignty upgrades / skyhooks views). A line member's bridge list through ESI is only: search for " » " in category `structure` → ids → one /universe/structures/{id} per id → name ("A » B - …"), solar_system_id, type_id (35841 = Ansiblex, per EVE Ref, secondary). The spec has no x-rate-limit on either route; its cache headers (x-cache-age, x-client-cache-ttl, x-server-cache-ttl) are declared but their values weren't read. Not settled by the spec: how many results the search returns at most (esi-issues #108 says fewer than expected). CCP's stance: the section above.

## Context
- Cradle of War (2026-09-22): Ansiblex bridges run on a capacitor charge that recharges slowly; cost by hull and distance. Changes use, not where lists come from. (source: https://www.eveonline.com/news/view/cradle-of-war-major-update-is-live, CCP, checked 2026-11-12)
- The structure-name form "A » B - name" is what EVE Toolkit and neocom-desk read; no CCP document found. UNVERIFIED: the owner, in game (a structure-browser copy pasted into the hand test).
- RIFT's on-screen form "system region security → system region security" already reads under D7 (region names and security numbers aren't system names); its Copy text is still to be seen.
- Our SSO apps (claude/reference/eve-sso-apps.md, 2026-11-07) have neither esi-search.search_structures.v1 nor esi-universe.read_structures.v1 registered, so Threat Vector can't run the search today without adding scopes.

## What it changes in 041
Folded into the plan as D6–D8 (2026-11-12): read SMT's two-line form (and any list with both directions) as one bridge, not a refused duplicate; on a line with a separator, the bridge is the two names around it; leading structure ids ignored. Not adopted: fetching a list from a URL or Dotlan id (a new outside host, the CSP's connect-src, and the DLA's data rules), the ESI search (D5 stands for 041, now also because CCP calls search-as-discovery abuse; "Find my bridges" with a login is its own later backlog item, blocked on that rule). Never real bridge lists in checks, mockups or the repo (made-up systems only).
